## Findings

### High

#### H6 (new) — ActualPrivateSpend circuit does not decompose `context_hash`

`zk/noir/vanta_private_pool_v2_actual_private_spend_entry/src/main.nr:78-113,115-171`

The circuit binds `context_hash` into `private_spend_public_input_hash` (the public input the verifier checks) but never decomposes it into component fields. The off-circuit code (`src/zk/actualPrivateTransactionRail.ts`) builds `context_hash = hash(merchant, denomination, settlementEpoch, nullifier)` — but the circuit itself only sees an opaque `Field`.

By contrast, `zk/noir/vanta_private_core_single_note_unshield/src/main.nr:145-152` *does* decompose: it includes `(release_destination_hi, release_destination_lo)` as separate Field inputs and computes the binding hash in-circuit. That is the right pattern, and the inconsistency between the two circuits is the finding.

**Why it matters.** Once tag-3 verifier wiring lands (C01 gate), the on-chain program will check that `public_input_hash` matches the proof's accepted public input. The validity of "this proof spends note X and pays merchant M" then depends entirely on whether the *off-circuit* `context_hash` construction is reproducible and not malleable by a relayer. If anything in the path from "user intent" to "`context_hash` Field handed to the prover" allows substitution — including a malicious or compromised relayer — the on-chain checker has no way to detect it, because the circuit doesn't constrain how `context_hash` was built.

**Severity.** High, because the C01 verifier landing is the moment this gap becomes load-bearing, and the circuit / proving / wire-up will be hard to change after a trusted setup ceremony is committed.

**Fix.** Bring ActualPrivateSpend into the Unshield pattern: take `(merchant_hi, merchant_lo, denomination, settlement_epoch)` as private inputs, recompute `context_hash` in-circuit with the same Poseidon shape, and assert equality with the public input. Add a fixture `invalid-context-hash-preimage` that flips one component byte and expects the circuit to reject. Mirror the existing `invalid-input-commitment-preimage` test shape.

### Outstanding from prior audit

#### H4 (carried) — `cfg!(test)` release/sentinel gating

`programs/vanta_private_pool_v2_spend/src/lib.rs:1023-1051, 2372-2384`

The SOL vault sentinel bypass in `require_vault_asset_record()` and the TAG_UNSHIELD release path both still use `cfg!(test)` to switch between fail-closed and helper behavior. As `AUDIT_2026-05-19.md` noted, this is currently safe because mainnet SBF is built without `--cfg test`, and the M4 inverted-`releaseEnabled` byte (which still reads "non-zero rejects, zero accepts" — the inverse of the comment's stated production intent) sits behind the same build-time gate.

The remediation is unchanged: introduce a runtime field on `pool_state` such as `verifier_wired: bool` and a `TAG_AUTHORITY_ENABLE_VERIFIER` instruction that an authority signs only after C01 audit acceptance. Until then, every release path is gated by something a build misconfiguration could flip silently. This is tracked as architecture blocker A1 and as a precondition for any meaningful mainnet pass.

### Medium

#### M6 (new) — Output commitments are bound, but destination/asset are not asserted in-circuit for spend

`programs/vanta_private_pool_v2_spend/src/lib.rs:439-528` and the ActualPrivateSpend circuit.

`process_spend_with_proof` reads `output0`, `output1`, `accepted_root`, `public_input_hash`, `verifier_key_hash` from instruction data and binds them to the (future) Groth16 verifier via `public_input_hash`. The output commitments themselves are Poseidon hashes of `(owner, asset, amount, blinding, derivation_tag)`, so the asset and amount are *implicitly* committed to the output. What is **not** explicitly verified in-circuit is that the proof binds the consumed-note's asset to the new outputs' assets, and that an `exit_destination` was tied into the proof when the spend is functionally a withdrawal.

This overlaps with H6 above for the payment-rail case. For the pure shielded-spend case, it is a documentation gap: the security argument relies on the verifier accepting a public-input-hash whose preimage the off-chain code constructs, and a reviewer cannot tell from the program source alone whether that preimage covers all the fields they would expect.

**Severity.** Medium — same fix shape as H6 (decompose into-circuit) and same urgency (must close before VK is committed).

#### M7 (new) — `TAG_REGISTER_VAULT_ASSET` is not idempotent for re-registration with different params

`programs/vanta_private_pool_v2_spend/src/lib.rs:848-920` calls `ensure_vault_asset_record()` (`lib.rs:1082-1180`), which short-circuits if the account is already initialized and matches expected data — but the *expected data* the function compares against is rebuilt from the caller's inputs. A second TAG_REGISTER_VAULT_ASSET for the same asset_id with different `vault_authority` / `token_program` / `mint` bytes would overwrite the prior record without flagging the mismatch in a release-blocking way.

Today TAG_UNSHIELD is fully fail-closed in production (`cfg!(not(test))`), so this cannot be exploited. After verifier wiring it can be — an operator who accidentally re-registers an asset would silently move the vault authority binding. Add an explicit `if account.initialized && record != expected → ERR_VAULT_ASSET_ALREADY_REGISTERED_WITH_DIFFERENT_PARAMS` before any state write.

#### M8 (new) — Operator services return raw `err.message` to clients

`operator/private-pool-v2-service-network.mjs:1678, 1970` and ~12 other locations.

`sendJson(response, 500, { error: err.message })` and `error instanceof Error ? error.message : String(error)` patterns shape error responses with the underlying exception text. For internal Bearer-authed clients this is fine. For the moment the service is exposed externally — or the moment a stack trace surfaces a file path or env-derived value — this becomes the kind of low-leverage information leak that turns into a reconnaissance vector. Replace with sanitized messages (`"validation failed"`, `"processing error"`) plus a server-side structured log (already present in most paths).

#### M9 (new) — Missing HTTP security headers on the live site

`curl -sI https://vantaprivacy.xyz/`:
- ✓ `X-Content-Type-Options: nosniff`
- ✗ No `Content-Security-Policy`
- ✗ No `Strict-Transport-Security`
- ✗ No `Permissions-Policy`
- ✗ No `Referrer-Policy`

The Cloudflare front is in front of Render. Both layers can add response headers. Set at least `HSTS max-age=31536000; includeSubDomains; preload`, a `Referrer-Policy: no-referrer`, a `Permissions-Policy` that disables sensors, and a tight `Content-Security-Policy` (`default-src 'self'; script-src 'self'; connect-src 'self' https://solana-rpc.publicnode.com https://*.onrender.com; frame-ancestors 'none'`). The SPA loads two chunks; CSP can be strict.

#### M10 (new) — CI does not gate `npm run build` or the privacy aggregates

`.github/workflows/privacy-audit.yml` runs `privacy-audit:tracker-check` and `frontend:operator-env-exposure-check` on PRs and pushes to main. It does *not* run:
- `npm run build` (so a TS error doesn't block a deploy)
- `npm run zk:review-guards-check` (the C01 gates)
- `npm run zk:feedback-loop-check` (the full ZK audit loop)
- `npm run truth:privacy-claim-gate`
- `npm run private-pool-v2:verify`

The local guards are honest because someone runs them locally, not because CI enforces them. One Doppler config blip or a forgotten gate update can sneak through. Add a `verify` job that runs `npm ci && npm run build && npm run truth:privacy-claim-gate && npm run zk:review-guards-check` on every PR.

## Path to "Fully Private Mainnet Ready"

This is the honest version. I am not going to pretend that any of these phases can be done from inside this sandbox or in a one-week sprint. Each phase has internal work Vanta can do unilaterally and external dependencies that gate it. I'll mark each step accordingly.

### Phase 0 — Cleanup (1 week, all internal)

Land the medium/low items above. Specifically:
1. Fix H6 in the ActualPrivateSpend circuit (decompose `context_hash`; add invalid-preimage fixture).
2. Add idempotency rejection to TAG_REGISTER_VAULT_ASSET (M7).
3. Sanitize operator error responses (M8).
4. Add CSP / HSTS / Referrer-Policy / Permissions-Policy to Cloudflare or Render (M9).
5. Expand CI to run `build` + `truth:privacy-claim-gate` + `zk:review-guards-check` on every PR (M10).
6. Close the L-tier items in one PR each.

None of this changes any privacy claim. None of it needs external review. It does reduce the number of things an auditor will list on first pass.

### Phase 1 — Close C01 (verifier wiring) (8–16 weeks, mostly external)

This is the largest single block of work, and every other privacy claim depends on it. The five gates are exactly as `docs/goals/2026-05-20-c01-h08-promotability/notes/promotability-map.md` lays out:

1. **Backend selection.** Done. `groth16-tag3-solana-v0` is committed in `docs/zk/c01-production-verifier-backend-decision.md` and the reserved tag-3 ABI matches.
2. **Production proof-format artifact and production VK hash for `vanta_private_pool_v2_actual_private_spend_entry`.** Requires: pin Sunspot/Nargo to a reviewed `1.0.0-beta.18` (or port to `beta.19`); install Sunspot + `GNARK_VERIFIER_BIN`; run a non-default trusted setup ceremony with toxic-waste mitigation; commit only the artifact refs (no raw key/proof/witness bytes). External dependency: ceremony participants, an audited build review, or an equivalently reviewed mitigation (e.g., one-shot KZG-derived universal setup).
3. **Verifier-adapter acceptance tests.** Inside the program: drive `process_spend_with_proof` with the production (proof, public_witness, VK) tuple, assert (valid → state mutates), (invalid → state byte-identical), (wrong public input hash → state byte-identical), (wrong VK hash → state byte-identical). The local-unsafe H6 Sunspot harness now covers valid mutation plus invalid-proof, wrong-public-input, wrong-verifier-program, and wrong generated-verifier/key-hash no-mutation cases against `/private/tmp` artifacts. That still does not count as production evidence; the production gate requires reviewed production proof/VK/public-witness refs and wrong-verifying-key no-mutation bound to production verifying-key hash semantics.
4. **SBF / live lineage.** Rebuild the spend SBF, redeploy to mainnet, reinitialize state, capture a transaction signature for the proof-enforced path. Cannot be done without mainnet keys and approval.
5. **Audit / reviewer acceptance.** External. Engage an audit firm; ABI, circuit, ceremony, and verifier-adapter test results are the input.

### Phase 2 — Program-owned PDA vault (4–8 weeks, internal-heavy)

Today Shield/Send/Swap/Unshield SOL custody is operator-trusted: the operator keypair owns the vault. The architecture target is a program-owned PDA vault where the program signs releases via the verifier-checked path. `programs/vanta_private_pool_v2_spend/src/lib.rs` already reserves `SOL_VAULT_SEED` and binds release to `sol_vault_pda + NATIVE_SOL_ASSET_ID_SENTINEL`. The blocker is: (a) C01 must close so the verifier can sign-off the release, and (b) the M4 `releaseEnabled` semantics must be inverted as the design comment promises.

Internal work: implement the runtime authority flip from cfg-gating to `pool_state.verifier_wired`; remove the `cfg!(test)` bypass once production tests can rely on the same code path; add Crucible coverage for `process_unshield` SOL release end-to-end. External work: post-audit live vault deployment.

### Phase 3 — Program-owned shared Merkle tree (6–10 weeks, mostly internal)

Today root provenance lives in `["vanta2root", pool_state, acceptedRoot]` PDA records — lineage metadata, not a program-owned tree. The architecture target (A3) is a program-owned Merkle tree where roots transition via verified state-update proofs, not operator-signed registrations. Concretely: a `TAG_APPEND_LEAF` path that takes a Groth16 proof binding `(old_root, new_root, appended_commitment, leaf_index)`, plus a circuit that proves the append-only transition. This is its own circuit + verifier story; it can run in parallel to Phase 1 but cannot be promoted until Phase 1 is closed.

### Phase 4 — Real recipient discovery (4–8 weeks, internal)

R9B and R9C landed the local viewing-key + proof-owner-key exchange scaffolds (`src/zk/vantaShieldViewingKey.ts`), but recipient discovery for live transfers is still operator-mediated. The target is one of: (a) an X25519-encrypted ciphertext-body discovery channel with on-chain commitment, (b) a stealth-address protocol where recipients scan a public ephemeral key without a server roundtrip, or (c) a relayer-mediated PSI scheme. (a) is the simplest if the ciphertext-body-hash binding (R9A) is already in place — verify, then ship.

### Phase 5 — Live anonymity set ≥ 1024 (volume-blocked)

The `currentDistinctCommitments: 2` in the public manifest is honest. There is no shortcut: this needs real volume of distinct commitments to land. The minimum 1024 threshold is configurable but the right number is what an external reviewer will accept as plausibly non-trivial. Until then, every claim must be "operator-trusted beta, no anonymity claim made."

### Phase 6 — External audit (4–8 weeks, external-only)

Engage a Solana-program-aware audit firm plus a ZK-circuit-aware audit firm (Cantina/OtterSec/Trail of Bits for the former; one of zksecurity.xyz / Veridise / 0xPARC for the latter). Scope: tag-3 verifier path + circuits + vault custody + tree state. Output: a signed report that maps directly onto the evidence-packet `auditReviewerAcceptanceRef` slots.

### Phase 7 — Live mainnet with proof-enforced release (2 weeks, external dependency)

Only after Phases 1, 2, 3 close and Phase 6 returns acceptance: rebuild SBF, deploy, reinitialize, capture lineage evidence, flip the `verifier_wired` runtime flag, run a real-funds proof-enforced shield → spend → unshield cycle, capture the transaction signatures, attest the audit manifest with the new commit and asset hash, drop the "operator-trusted beta" copy across all lanes.

### What "fully private mainnet ready" actually means

If "fully private" is read maximally — meaning anonymity ≥ N, all lanes (Shield/Send/Swap/Unshield/Pay/Strategy) running through proof-verified paths, no operator-trusted fallback anywhere, recipient discovery off the operator path — then realistic calendar is **8–14 months** from today, gated mostly on (i) the trusted setup ceremony for Phase 1, (ii) the audit cycles for Phase 6, and (iii) bootstrapping the anonymity set in Phase 5. Vanta can move Phases 0/2/3/4 in parallel inside that window; Phase 1 is the critical path because Phases 2-4 do not promote without it.

If "fully private mainnet ready" is read as "one lane, one minimal claim, audit-defensible" — Shield + actual-private-spend with anonymity ≥ 1024 and a proof-enforced exit — calendar shrinks to **6-9 months** because Phases 2/3/4 only need to cover that one lane. This is what `docs/goals/2026-05-20-c01-h08-promotability/notes/promotability-map.md` calls the "shortest honest path."

There is no shortcut where you ship "production-private mainnet" in a few weeks without losing the fail-closed truth boundary that is currently the strongest thing about the repo. Don't.
