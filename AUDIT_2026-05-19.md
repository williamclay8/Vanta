## High Severity Findings

### H1. The "client-side programmatic privacy" claim is fictional

**Evidence.** The repo ships its own verification script for this claim:

```
$ node scripts/verify-client-side-proving.mjs
✅ indexerClient.ts exists and exports getCurrentRoot
❌ liveShieldBridge.ts imports indexerClient
❌ liveShieldBridge.ts uses USE_INDEXER flag
❌ liveShieldBridge.ts has fallback logic
❌ liveSendBridge.ts ... (same)
❌ liveSwapBridge.ts ... (same)
❌ liveUnshieldBridge.ts ... (same)
=== Summary ===
Passed: 2 / Failed: 12
```

Likewise `node scripts/check-vanta-indexer-client-integration.mjs` reports 16 explicit ❌ findings.

**Root cause.** `git show 5684035d` shows the "feat: complete client-side programmatic privacy implementation" commit inserting code like this into `src/zk/liveSendBridge.ts`:

```ts
import {
import { getCurrentRoot, fetchOperatorRoot } from "./indexerClient";
const USE_INDEXER = import.meta.env.VITE_USE_INDEXER === "true";
async function getRootForliveSendBridge() { ... }
}
import { getCurrentRoot } from "./indexerClient";
}
  createCanonicalNote, ...
```

That is not valid TypeScript — there are stray `}` tokens inside the imports block, a duplicate import, and the helper function is declared inside the imports list. The same shape appears in `liveSwapBridge.ts` and `liveUnshieldBridge.ts`. The file would not have compiled.

Commit `d5786407 "Harden programmatic privacy gates"` then *removed* every one of those lines from each bridge — but did not add a working replacement. The result is:

- `src/zk/indexerClient.ts`: exists, exports `getCurrentRoot`, `fetchIndexerRoot`, `fetchOperatorRoot`. Referenced nowhere in `src/` outside of itself.
- `src/zk/clientProver.ts`: a near-duplicate of indexerClient plus a `generateShieldProof` stub whose `SHIELD_CIRCUIT` is an empty object literal (`{ /* compiled circuit JSON */ } as any`). Referenced nowhere.
- `liveShieldBridge.ts`, `liveSendBridge.ts`, `liveSwapBridge.ts`, `liveUnshieldBridge.ts`: contain no `getCurrentRoot`, no `VITE_USE_INDEXER`, no `fetchOperatorRoot` calls.

The shipped `FINAL_IMPLEMENTATION_SUMMARY.md`, `PRODUCTION_READINESS_CHECKLIST.md`, and `PRODUCTION_SIGNOFF.md` describe this work as complete and signed off. None of those documents are accurate.

**Why it matters.** Two ways:
- (a) Any future reviewer reading the checklist will be misled into believing the privacy flow is client-side. It is not — the live SPA still routes through `vanta-prod-private-pool-v2-operator.onrender.com`.
- (b) These three docs are the kind of artifact that an auditor or partner will quote back in due diligence. Leaving them on `main` is the same shape of overclaim that N3 was meant to fix.

**Recommendation.** Either re-do the integration properly (gate by `VITE_USE_INDEXER`, fetch from the indexer service that is actually deployed, fall back to operator with the bearer token routed through it) or delete `src/zk/indexerClient.ts`, `src/zk/clientProver.ts`, `operator/light-public-indexer.mjs`, `scripts/verify-client-side-proving.mjs`, `scripts/check-vanta-indexer-client-integration.mjs`, `render-indexer.yaml`, `FINAL_IMPLEMENTATION_SUMMARY.md`, `PRODUCTION_READINESS_CHECKLIST.md`, `PRODUCTION_SIGNOFF.md`, and the "Production sign-off received" claim from `5684035d`. The cleanest move is the deletion; the local hardening work that's *actually* real is already tracked in the 2026-05-14 audit tracker.

### H2. `vanta-light-public-indexer.onrender.com` is dead

`/health`, `/root`, and `/` all return HTTP 404. There is no service listening at that URL today (either un-deployed or Render free-tier expired). The hard-coded default in `indexerClient.ts` would fall through to `fetchOperatorRoot()`, but `VITE_OPERATOR_URL` is empty in the live build, so `getCurrentRoot()` would return null on every call. The checklist line `[x] Deployed to production on Render` is false.

### H3. TAG_UNSHIELD zero-nullifier check missing

`programs/vanta_private_pool_v2_spend/src/lib.rs:1965–1985` reads `nullifier = rest[0..32]` and immediately proceeds to derive the marker PDA. There is no `is_zero_hash(nullifier)` rejection here, unlike TAG_SPEND_WITH_PROOF and TAG_UNSHIELD_RESERVED_RELEASE_PREFLIGHT which do reject zero. Today, `cfg!(not(test)) => ERR_UNSHIELD_NOT_WIRED` short-circuits the path before the CPI, so it is not exploitable. Once the verifier is wired, the absence of the zero check means a proof over `nullifier = 0x00..00` would derive a fixed marker PDA — a candidate double-spend vector. Add the zero-hash guard at the same point Send/Spend has it, even though it is currently behind a fail-closed gate.

### H4. Sentinel bypass and verifier wiring are gated by `cfg!(test)` rather than runtime state

Both the SOL vault sentinel bypass in `require_vault_asset_record()` (lines 759–772) and the TAG_UNSHIELD release path (lines 1998–2000) use `cfg!(test)` / `cfg!(not(test))` to switch between fail-closed and test-helper behavior. The intent is clear, and the SBF binary deployed to mainnet is built without `--cfg test`, so the path is safe in production. However:

- An accidental build with `--cfg test` or the wrong feature set flips the gate live.
- A reviewer scanning for "what enables the release path" has to know to look for `cfg!()` macros rather than reading a runtime field.

Moving these gates to a runtime field on `pool_state` (e.g. `pool_state.verifier_wired: bool` set only by an authority-signed instruction post-audit) would be both clearer and more resistant to build-flag accidents. Tracked under A1 in the architecture backlog but worth calling out explicitly.

### H5. Helius RPC project URL hard-coded in the bundle

`assets/private-core-runtime-QWKV0SmO.js` contains the string literal `https://yoko-lx0bix-fast-mainnet.helius-rpc.com`. This is your project subdomain. Anyone who downloads the public JS bundle can use this endpoint to make RPC calls against your paid quota and to send traffic to Helius that they then learn from.

The fall-through to `solana-rpc.publicnode.com` exists, but it only fires if the Helius URL is unset at build time — the production build clearly sets it. Either:

- Proxy the Helius URL through your own operator (so the secret/project ID is server-side), or
- Use a session-token-gated Helius endpoint (the Premium plan supports per-token URLs), or
- Pull the RPC URL at runtime from `/config` instead of baking it into the bundle.

This is a build-pipeline hygiene problem, not a privacy-model problem, but it directly leaks operator economics and per-user RPC traffic patterns.

## Medium Severity Findings

### M1. `operator/light-public-indexer.mjs` returns a hard-coded zero root on the fallback path

```js
const rootData = {
  merkleRoot: "0x0000...0000",
  nullifierRoot: "0x0000...0000",
  timestamp: Date.now()
};
res.json(rootData);
```

A client that asks `getCurrentRoot()` with `useIndexer=true`, fails open to this server, and then *believes* the all-zero root is real, will compute a proof against a non-existent tree. The `isValidRootData` check in `indexerClient.ts` passes a zero root as "valid" because it's only checking field shapes. Add a sentinel rejection client-side or have the server return 503 when it has no upstream operator configured. Right now nothing calls this code anyway (H2), but if you redo the integration this trap is waiting.

### M2. `operator/light-public-indexer.mjs` has wide-open CORS and in-memory rate limiting

`app.use(cors())` allows any origin; the in-memory rate-limit Map loses state on every restart and is per-replica. Use `cors({ origin: [VITE_SITE_ORIGIN] })` and either `express-rate-limit` with Redis backing or fronting via Cloudflare / Render's edge rules. The same comments apply to any future iteration of this server.

### M3. Audit manifest at `/.well-known/vanta-audit.json` is stale relative to the live deploy

The manifest references `verifiedCommit: 7635c9b...` and `live_main_asset: index-C5gkBpDx.js`. The live site is serving `index-l4ihLMxe.js`, meaning a newer deploy has happened without the manifest being re-attested. The manifest itself prescribes the rerun procedure (`rerun live verification for newer commits`), but the procedure hasn't been run. Either re-attest with the new commit / asset, or revert the deploy to the attested one. Leaving them out of sync turns the manifest into a polite lie.

### M4. Inverted release-enabled semantics in `require_vault_asset_record`

```rust
if asset_data[VAULT_ASSET_RELEASE_ENABLED_OFFSET] != 0 {
    return Err(...);
}
```

The comment block says "Production: this path must require valid registered entry (kind=2, releaseEnabled)". The check rejects when the byte is non-zero, i.e. it requires `releaseEnabled = 0` to proceed. If the comment is the source of truth, the comparison is inverted and the gate will reject every properly-registered vault once TAG_REGISTER_VAULT_ASSET is wired. If the code is the source of truth, then the comment is misleading. Either way, please pick one and update the other.

### M5. Verifier-key hash is caller-supplied at TAG_SPEND_WITH_PROOF

`rest[160..192]` is the verifier_key_hash; it's used to derive the PDA seed `["vanta2vkey", pool_state, verifier_key_hash]`. The check binds the verifier-key account to the supplied hash, but it doesn't bind the *hash itself* to the proof. The transitive binding works only because the future Groth16 verifier will reject a proof whose public-input hash doesn't match. That's fine — but it means the safety of TAG_SPEND_WITH_PROOF rests entirely on the verifier module getting the public-input → verifying-key linkage right. Worth documenting explicitly in the SBF ABI doc, because today it lives only in reviewer heads.

### M6. Live indexer requires a Bearer token; SPA has none

`https://vanta-prod-private-pool-v2-indexer.onrender.com/v1/*` returns 401 without `Authorization: Bearer <token>`. The bundle does not contain any tokens that would let a browser pass that check (verified by grep for `Bearer`, `Authorization`, JWT-shaped strings, `pp2_`, `tok_`, etc). Consequently, the live SPA cannot independently verify roots, fetch nullifier state, or check the anonymity set from the client. Every privacy operation routes through the operator service, which holds the keypair. This is the expected operator-trusted-beta posture and matches A2-OPERATOR-KEYPAIR-CUSTODY — but it is the *opposite* of the "programmatic privacy" claim in the recent commits. Until you replace the operator-keypair vault custody with a program-owned PDA, the privacy claim must remain "operator-trusted beta".

## Low Severity Findings / Hygiene

### L1. `src/zk/clientProver.ts` ships a stub `SHIELD_CIRCUIT = {}`

Even ignoring H1, the file is misleading: `generateShieldProof()` invokes `Noir` with an empty circuit object and would throw at runtime. Delete or replace.

### L2. `redactLiveShieldRecordForPersistence` overwrites `commitment` with the literal string `"redacted:commitment"`

`liveShieldBridge.ts:351`. This is consistent with the privacy-minded storage policy, but a subsequent read of `record.artifacts.commitment.value` will return the literal string `"redacted:commitment"` rather than the actual commitment hash. The downstream code that calls `getLatestCanonicalShieldSnapshot()` (line 240) returns that redacted string as the `root.value`. If anything down the line proves against this snapshot, it will prove against a fake root. Confirm no proof path consumes the persisted record's `commitment.value`; if it does, the redaction policy needs to recompute on-the-fly rather than store a sentinel.

### L3. `helmet()` is configured with defaults — no CSP

`operator/light-public-indexer.mjs:9` calls `helmet()` with no options. Production deployments should set `contentSecurityPolicy` explicitly; the default disallows inline scripts, which is fine for a JSON-only API, but no `Strict-Transport-Security` is set either. Small fix.

### L4. `process.env[...]` lookups happen at module load in `indexerClient.ts`

If the integration is ever revived, switch to a `getEnv` call inside `getCurrentRoot` so that test-time and ESM-rewrite scenarios don't cache an empty value. Today the values come from Vite's `import.meta.env` at build time, so a runtime override isn't possible.

### L5. The Render service IDs are in the public audit manifest

`renderServiceId: srv-d7j3ggqqqhas739for80` and the deploy ID `dep-d834ce4vikkc73fb2ep0` are in `/.well-known/vanta-audit.json`. These don't grant access on their own, but they make targeted scraping or spoof-deploy attempts easier. Consider scrubbing them or keeping only an opaque attestation hash.

## Recommended Order Of Operations

1. **Delete or repair the indexer / clientProver dead code path and the misleading checklist/signoff docs.** This is a 1-hour change that stops the website from claiming something untrue about itself. If you want to keep the path open for later, gate the docs behind a `STATUS=draft` label.
2. **Add the zero-nullifier check to TAG_UNSHIELD.** A two-line change today, while it's still test-only, removes a real future double-spend vector. Add a no-zero-nullifier proof fixture to Crucible.
3. **Re-attest `/.well-known/vanta-audit.json` against the current live deploy** (or revert the deploy to the attested commit).
4. **Move the Helius RPC URL out of the bundle.** Either proxy or fetch from a `/config` endpoint at runtime. This is a build-pipeline change, not a code change.
5. **Decide on the runtime gating story for SBF release paths.** Either commit to `cfg!(test)` and document loudly, or migrate to a `pool_state.verifier_wired` flag that an authority instruction can flip post-audit.
6. **Fix the `releaseEnabled` comment-vs-code mismatch in `require_vault_asset_record`** before TAG_REGISTER_VAULT_ASSET goes live; otherwise the whole release path will be unintentionally bricked or unintentionally open.

Everything else on the kanban tracker — proof-verified on-chain release, program-owned PDA vault, fresh-address exit, ≥1024 anonymity set, audit acceptance — is correctly marked blocked-architecture or blocked-volume, and there is no way to close those with local code edits. They are the right blockers to keep blocked.
